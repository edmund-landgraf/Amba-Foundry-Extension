# Foundry v14 + PF2e: complete AMBA/WGUI source-to-target matrix

**Audit date:** 2026-10-23  
**Scope:** everything relevant to the AMBA adventure/PC push, including PC mechanics, assets, encounters, and custom creatures. This is a **domain-level and field-level export inventory**, not a claim to enumerate every internal property of every Foundry model.  
**Status:** source/official documentation verified; no end-to-end import into a running Foundry world yet.

## 0. Executive decisions

1. **AMBA is canonical for authored/adventure content and the PC export snapshot.** Wanderer's Guide (WG/WGUI) is an optional upstream character builder and lookup backend, not a required runtime application for Foundry users.
2. **Foundry v14 + the installed PF2e system is authoritative for playable mechanics.** Build native `Actor(type:"character")`, `Actor(type:"npc")`, `Item` documents, `Scene` Levels, and Tokens/Combats. Do not ship our own PF2e rules engine.
3. **WG's Supabase Edge Functions plus AMBA PC functions provide most *source material*; not automatically a valid Foundry build.** WG's `find-character` returns the raw saved row. Its much richer v4 JSON `{version:4,character,content}` with calculated data is **generated by the WGUI frontend** (executes character operations). WG `find-*` endpoints retrieve missing referenced feats, spells, gear, books, traits, etc. Therefore normalization + native Foundry Item resolution are still required.
4. **Persistent damage such as persistent fire is native PF2e.** Existing PF2e code stores the condition's damage type/formula/recovery DC, rolls damage at end of turn to chat, and exposes a recovery check which removes the condition on success. **Automatic HP deduction and unattended NPC recovery checks are not universally built-in**; do not claim hands-free automation without testing optional modules/settings.
5. **No extra WG → Foundry dependency in the live bridge.** AMBA should build a complete, enriched, permissioned export payload server-side, so the Foundry module needs one authenticated AMBA source and can work offline from WG after import.
6. **GPL caution:** WGUI [GPL-3.0](https://github.com/wanderers-guide/wanderers-guide/blob/main/LICENSE) sources are used for API/schema research. Do not paste, vendor, or copy implementation code into our separate repo without legal/license review. Consuming WG's HTTP API and independently mapping public schemas is not the same as redistributing GPL code.

## 2. Source availability notation

- **A:** Already present or derivable in AMBA's stored PC / `Pf2eCharacterSheetData`; includes WG imports, AMBA-authored sheets, metadata, and artifacts.
- **W:** Raw WG character JSON (from authorized `find-character` or an optional imported source JSON copy in AMBA).
- **W4:** Full compiled WG v4 export (`character` + `content`); may exist as optional copied JSON but is **not** just an Edge Function response.
- **WF:** WG `find-*`/ `search-data` Edge Function, authenticated and subject to content-source visibility and per-character access.
- **P:** AMBA PF2 Search service (port 3333) for canonical PF2 creature/stat lookup and supplemental content.
- **F:** Foundry PF2e world/compendium native content, required for actual rule item construction.
- **G:** GM/user choice or metadata not inferable from static source.

### Confidence/readiness notation

- **Available:** data shape confirmed in an existing source; individual character rows may still omit values.
- **Resolve:** source exists but must map to valid Foundry source Items/rule schemas.
- **Partial:** information exists, but no proven complete transform; may need human review.
- **GM:** requires player/GM assignment or choices.
- **Runtime:** preserve/control in Foundry after first import; not a source to reapply repeatedly.

### Key practical point

**Foundry does not want AMBA's character's calculated AC/attack/save numbers as the main rule source.** Foundry's system calculates them from *native class, ancestry, feats, weapons, spells, inventory, effects and build choices*. Use WG-derived statistics as **validation checkpoints** during import. A full character with all correct native Items is vastly more functional than an Actor whose displayed totals were pasted from a stat block.

### Why WGUI v4 JSON matters

The frontend's [`json-v4.ts`](https://github.com/wanderers-guide/wanderers-guide/blob/main/frontend/src/process/export/json/json-v4.ts) produces:

```text
version: 4
character: { name, level, details, inventory, operation_data, spells, ... }
content: {
  feats_features, character_traits, languages, senses,
  weapons, inventory_flat, spell_raw_data, spell_sources,
  spell_slots, spells, focus_spells, innate_spells,
  size, speeds, max_hp, ac, resist_weaks, proficiencies,
  attributes, raw_data_dump, companions, ...
}
```

The `content` object is computed in the **WGUI frontend** by running the operations engine, so **Edge Functions alone do not guarantee it**. Strategies for AMBA:

1. If AMBA stored a full WG v4 JSON copy for a PC, extract and validate its rich `content` as supplemental data.
2. Otherwise use the AMBA `wg-friendly/v1` normalized sheet, `wgSelections`, `wgImportLeftover`, and optionally the authorized raw WG character row.
3. Resolve referenced IDs through WG `find-*` calls **server-side** when permission and connectivity permit, while preserving unresolved choices for review.
4. Use the **native Foundry PF2e Items** as the ultimate rule source; use WG derived totals to detect mismatches.
5. Report per-PC readiness: identity/mapped Items/spells/gear/choices/HP/conditions/companion coverage with provenance.

## 8. Important constraints for playable Foundry PCs

### Native Item dependency

From [PF2e character document](https://github.com/foundryvtt/pf2e/blob/v14-dev/src/module/actor/character/document.ts), Foundry PC Actors explicitly accept build Items such as `ancestry`, `heritage`, `background`, `class`, `deity`, `feat`, physical equipment, `spellcastingEntry`, `spell`, `action`, `lore`, and `kit`. The Actor's level, HP/resources, biography, skills, build boosts, and ownership are populated through version-specific PF2e source fields (see [character data types](https://github.com/foundryvtt/pf2e/blob/v14-dev/src/module/actor/character/data.ts)).

**No guaranteed 1:1 WG ID → Foundry UUID mapping.** Resolve by explicit prior mapping/source book/version, then exact normalized name + level/type, then user-approved choices for ambiguous/homebrew cases. Do not overwrite derived AC/saves/strikes with raw WG display values.

### Native spells

A usable spell is a PF2e `spell` Item attached to a proper `spellcastingEntry` with the correct location/source. [PF2e spell source schema](https://github.com/foundryvtt/pf2e/blob/v14-dev/src/module/item/spell/data.ts) includes traditions, level, area, targets, duration, damage categories, defenses, heightening and overlays. WG's spell data can find matching named spells and track prepared/casts, but the **Foundry source Item** carries much of the automation.

### Persistent damage and ongoing effects

The PF2e [condition source](https://github.com/foundryvtt/pf2e/blob/v14-dev/src/module/item/condition/document.ts) explicitly implements a `persistent` damage value with damage type, roll formula and recovery DC. `onEndTurn` sends damage to chat; `rollRecovery` performs a flat check and clears condition on success. Its old separate [Persistent Damage module](https://foundryvtt.com/packages/pf2e-persistent-damage) was discontinued when PF2e integrated the feature.

**Export requirement:** import native source spells/actions, and when adding *initial* conditions ensure exact formula/type/DC are known. WG's generic `ConditionSchema {name,description,value,source,...}` does **not** by itself guarantee a reliable persistent-damage formula/recovery DC. Let Foundry manage combat/rounds after play starts. Optional automation for auto-HP application is a separate user-setting/module decision and must be smoke-tested.

### Other gaps that need conscious decisions

- WG `details.info` may include private/character biography data. Authorize/redact appropriately; do not export entire sensitive WG row.
- WG `details.api_clients`, `user_id`, JWT/access tokens, API keys, and raw client grants are **never exported to Foundry**.
- Character-source ownership, Foundry game-user ownership, companion ownership and what players can see are different access systems.
- WG rich item metadata (including homebrew/runes) may not match any installed Foundry pack. Preserve readable descriptive fallback plus explicit unautomated warnings.
- Spellcasting/companion handling is likely the highest-complexity part of faithful PC imports. Budget runtime tests for different class preparations and editions/remaster variants.
- Content licenses matter: do not indiscriminately republish the WG/Paizo catalog inside an AMBA download; prefer Foundry's installed licensed compendia and lawful user-authored data.

## 9. Build contract and tests

```text
AMBA PC (database + current structured sheet)
     + optional already-copied WG v4 JSON
     + optional permissioned WG `find-character` + catalog find-* calls
     + optional PF2 Search supplements for creatures
          |
          v
 AMBA `buildFoundryPcDTO()`: normalized fields, references, provenance,
   source hash/revision, completeness, warnings, media refs
          |
          v
 Foundry bridge read-only preview
   (F compendium UUID mapping, ambiguity, score, unresolved rows)
          |
          v
 Native PF2e Actor('character') + embedded Items + Journals + optional Token
          |
          v
 Foundry runs the character; AMBA owns source/adventure, not live HP
```

**Acceptance tests:**

1. Fighter L1 with weapon/armor: correct ancestry/background/class, weapon Item, skills, AC, strike, HP; all calculated stats plausibly match WG preview.
2. Prepared caster: casting entry + correct prepared spells and expended slots.
3. Spontaneous caster: known spells, repertoire/signature heights and slot counts.
4. Focus/innate caster: correct grants/uses/focus points and action buttons.
5. Feats/homebrew: resolution report shows exact source vs custom/unresolved; no silent omitted feat.
6. Companion: separate Actor with correct association/ownership and tokens.
7. Persistent fire: native PF2e condition retained through rounds; end-turn chat damage; recovery check; **do not assume automatic HP deduction**.
8. Imported sheet **without copied WG JSON** still yields a useful actor preview and a list of missing selections.
9. User reimports after playing: current HP/equipment usage, conditions, spell slots, position, and player ownership are **not overwritten**.
10. Reject redacted/private data leakage and unauthorized WG character access.
11. The AMBA-only route works when WG is offline after previous import.
12. Foundry v14 build and PF2e version are pinned for integration tests; no assertion of verified runtime until tests succeed.

## 10. What is done vs still to code

**Verified in source:** WGUI data schema; Edge Function routes/auth; client-generated v4 export; AMBA WG JSON import and structured PF2e sheet; PF2e native target Actor/Item/condition support.

**Not done:** Foundry PC DTO API; WGUI enrichment/prefetch caching under a Foundry-specific scope; Foundry Item resolver; exact version-specific Foundry Actor creation; full PC and custom creature import; Foundry runtime test; optional live WG combat syncing.

**Recommendation:** Implement a pure, side-effect-free **`buildFoundryPcDTO` and test suite inside AdventureMakerByAct first**, using three PC fixtures (martial, prepared caster, homebrew). Implement Foundry resolver + native Actor writer in our separate extension, after a dry-run preview. This shares the AMBA/WG import research without coupling Foundry to a WG session or a second rules engine.
